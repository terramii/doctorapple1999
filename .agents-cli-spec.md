# Agent Spec

## Overview

Build a local hackathon prototype named **Doctor Apple** that automates clinic pre-registration for scheduled and walk-in patients. The agent will use the Agnes AI API for document understanding and conversational orchestration, MongoDB for prototype persistence, and deterministic local tools for patient lookup, package eligibility, questionnaire prefill, and billing classification.

The system prepares registration data before the patient reaches the counter. Clinic staff must still verify the patient's physical identity and e-card in person before approving registration or issuing a queue number.

The prototype must have an integration boundary that can later be exposed to Microsoft Copilot Studio through HTTP actions or a custom connector.

## Example Use Cases

1. A scheduled patient uploads a synthetic medical chit. The agent extracts identifiers and insurer codes, finds the patient, determines the covered screening package, flags uncovered requests, prefills the appropriate questionnaire, and creates a pending registration for staff review.
2. A walk-in patient signs up or signs in, searches or creates their profile, submits registration details, and receives a pending status until staff complete in-person identity verification.
3. Clinic staff review extracted fields, discrepancies, allergies, package coverage, and proposed billing. They approve or correct the record and record completion of the mandatory physical identity check.
4. An uncertain or conflicting document match is not guessed. The agent returns the evidence and routes the case to manual review.

## Tools Required

### Agnes AI adapter

- Purpose: structured extraction from medical chits and natural-language orchestration.
- Authentication: server-side `AGNES_AI_API_KEY`; never exposed to client code or logs.
- Compatibility: use the OpenAI-style interface documented by Agnes with bearer-token authentication.
- Base URL: default `AGNES_AI_BASE_URL` to `https://apihub.agnes-ai.com/v1`, while retaining the environment override.
- Model: default to the generally available Agnes 2.5 Flash text/multimodal model because Agnes documents it for agent workflows, tool calling, and multimodal understanding. Keep the exact API model identifier configurable through `AGNES_AI_MODEL` and verify it with a models/API request before the first live inference.
- Contract: request structured JSON validated against an application schema; invalid or incomplete output is rejected or escalated.

### MongoDB

- Purpose: store seeded synthetic patients, user accounts, pending registrations, questionnaire prefills, staff decisions, and audit events.
- Authentication: server-side `MONGODB_URI`.
- Prototype: support a local MongoDB instance; optionally accept a MongoDB Atlas URI without code changes.
- Indexes: unique normalized email for accounts; unique normalized NRIC/FIN/passport identifier for patient records where appropriate.

### Deterministic clinic tools

- Reuse and wrap the supplied clinic automation scripts for document text extraction, patient lookup, eligibility/package matching, and questionnaire prefill.
- Package and billing rules are authoritative application logic, not free-form LLM decisions.
- Compare document-requested tests with covered tests and return explicit uncovered items.

### Authentication service

- New users can register and existing users can sign in.
- Passwords must be salted and hashed; plaintext passwords are never stored.
- Authentication responses must not reveal whether sensitive patient identifiers exist.
- Role separation is required for patients and clinic staff.

### Local API and interface

- Provide a local server API for authentication, document processing, registrations, review, and approval.
- Reuse the existing prototype UI where practical, replacing hard-coded session data with API-backed records.
- Keep business operations behind stable JSON endpoints suitable for later Copilot Studio custom-connector/OpenAPI integration.

## Constraints & Safety Rules

1. Physical identity verification and e-card validation are always performed in person by clinic staff and can never be marked complete by Agnes or another automated process.
2. The system performs administrative assistance only and must not diagnose, recommend treatment, interpret clinical results, or make other clinical decisions.
3. Eligibility and billing are calculated by deterministic rules. Low-confidence extraction, unknown codes, contradictions, or uncovered costs require staff review.
4. Drug allergies are always displayed as prominent safety warnings to staff. The agent must not infer absent allergy information.
5. Full NRIC/FIN/passport numbers, passwords, API keys, session tokens, and health data must not appear in logs. Identifiers are masked in user-visible audit events.
6. Agnes keys and MongoDB credentials remain server-side and are loaded from ignored environment files.
7. Validate file type and size, sanitize filenames, and reject unsupported or malformed uploads.
8. Apply least-privilege access by role. Patient users can access only their own records; staff actions are audited.
9. Any patient-facing prefill remains editable/confirmable by the patient, and staff corrections retain an audit trail.
10. Synthetic data is used for the prototype. Production use requires a formal PDPA/security review, encryption, retention rules, consent flows, and approved healthcare-system integrations.

## Success Criteria

1. Seed the supplied synthetic patient and questionnaire data into MongoDB reproducibly.
2. Register a user, sign in securely, and maintain an authenticated local session.
3. Process at least one supplied medical chit end-to-end into a validated pending registration.
4. Correctly resolve every insurer/TPA code and age-band rule supplied in the clinic automation skill.
5. Display drug-allergy warnings and explicitly list uncovered tests.
6. Prevent registration approval until a staff user records in-person identity verification.
7. Escalate unknown codes and ambiguous/conflicting extraction rather than inventing an answer.
8. Keep secrets and full sensitive identifiers out of logs and version-controlled files.
9. Pass deterministic unit/integration tests and agent behavioral evaluations for a normal case and a safety/escalation case.
10. Include a Copilot Studio migration guide covering the OpenAPI/custom connector boundary, authentication, actions, environment variables, and human-approval flow.

## Architecture & Data Flow

1. Patient uploads a chit or enters walk-in details through the local UI.
2. The backend extracts local document text and sends only the necessary content to the Agnes adapter for schema-constrained field extraction.
3. Deterministic tools query MongoDB, resolve eligibility/package rules, compare requested and covered tests, and generate questionnaire prefill data.
4. The backend stores a pending registration plus a redacted audit trail.
5. Staff review discrepancies and safety warnings, inspect the physical ID/e-card, and explicitly approve or correct the registration.
6. Approved JSON operations later map to Copilot Studio actions without moving core healthcare rules into prompts.

## Edge Cases to Handle

- Patient not found, duplicate patient, or duplicate account.
- Name, date-of-birth, or identifier mismatch between chit and database.
- Unknown insurer/TPA code or age exactly on a package boundary.
- Missing allergy value versus explicitly declared no known drug allergy.
- Requested tests not covered by the resolved package.
- Agnes timeout, rate limit, malformed JSON, low-confidence extraction, or unavailable service.
- MongoDB unavailable or duplicate-key conflict.
- Unsupported, empty, oversized, or maliciously named upload.
- Patient attempts to access another patient's record or mark identity verification complete.

## Microsoft Copilot Studio Migration

- Expose the stable backend operations through an OpenAPI document and a Copilot Studio custom connector or agent tool.
- Keep MongoDB access, Agnes credentials, eligibility rules, password handling, and audit logic behind the backend API.
- Represent staff approval as an explicit action with role authorization, not as a conversational assertion.
- Map Copilot topics/actions to: authenticate, extract document, find patient, resolve eligibility, generate prefill, create pending registration, get review status, and staff approve/correct.
- Provide environment and deployment guidance after the local prototype is validated; do not deploy during this phase.
